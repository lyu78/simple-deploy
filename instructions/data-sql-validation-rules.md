# Правила валидации data SQL

Этот документ фиксирует бизнес-правила, которые `simple-deploy` проверяет для SQL-скриптов
backend repo перед сборкой или ручным применением data SQL. Проверки работают read-only:
они читают SQL и файлы backend repo, формируют отчет и завершаются ошибкой при нарушениях.
Они не исправляют SQL, не меняют backend repo и не нормализуют данные автоматически.

Источник актуальных SQL задается через `BACKEND_SOURCE_REPO_PATH`; ожидаемый каталог:

```text
docs/database/scripts
```

## Классы SQL

`full-state` приводит таблицу или контролируемый набор таблиц к эталонному состоянию между
DEV и TEST. Для таких скриптов допустимы:

- `TRUNCATE + INSERT`, если скрипт владеет полным содержимым целевой таблицы;
- `DROP TABLE IF EXISTS + CREATE TABLE + INSERT`, если скрипт пересоздает полностью
  принадлежащую ему таблицу;
- `INSERT ... ON CONFLICT (id) DO UPDATE`, если перезапись по идентификатору является
  намеренным способом выравнивания контуров;
- `MERGE`, если он используется как явный upsert.

`insert-if-missing` только добавляет отсутствующие бизнес-объекты. Для таких скриптов:

- требуется `INSERT ... ON CONFLICT DO NOTHING`;
- запрещен `TRUNCATE`;
- запрещена массовая перезапись уже существующих строк.

`update/backfill` повторно применяет изменения к существующим строкам. Такой SQL должен иметь
устойчивое условие `WHERE` и не должен накапливать побочные эффекты при повторном запуске.

## Каталоги

Для catalog/full-state скриптов `simple-deploy` проверяет дубли по известным уникальным
business keys. Если generated SQL содержит две разные строки, конфликтующие по одному
business key, preflight должен упасть до сборки.

Примеры известных ключей:

- `app_ip_subcompany_catalog_contractsubject`: `title`;
- `app_ip_subcompany_catalog_contracttype`: `title`;
- `app_ip_subcompany_catalog_region`: `code`;
- `app_ip_subcompany_catalog_contractor`: непустой `tin`.

Список ключей поддерживается в `simple-deploy`, потому что это часть контракта проверки.
Если backend schema меняет unique constraints или добавляет новые catalog full-state скрипты,
карту ключей нужно обновить вместе с тестами.

## Новые объекты

Скрипты под `insert_new_objects/**` относятся к классу `insert-if-missing`.
Они не являются full-state dump и не должны очищать целевые таблицы.

Ожидаемый порядок зависимостей для связанных объектов:

1. `objectplanning`;
2. `prw_objectprw`;
3. `cc_objectcc`.

Нарушение порядка может привести к ошибкам внешних ключей, например когда `cc_objectcc`
ссылается на еще не вставленный `prw_objectprw`.

## Поведение preflight

При нарушении проверка должна вывести:

- путь SQL-файла относительно backend repo;
- имя правила;
- таблицу и business key, если нарушение связано с каталогом;
- строки и значения, если их можно восстановить статически.

После отчета dry-run/build завершается ненулевым кодом до создания или применения data SQL
artifacts. Исправление SQL выполняется отдельно в backend repo владельцем этих скриптов.
