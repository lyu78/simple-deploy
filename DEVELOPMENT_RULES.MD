# Правила разработки Simple-Deploy

## Назначение

Этот файл фиксирует правила работы с кодом, документацией, историей Git и
взаимодействием с AI-агентом в проекте `simple-deploy`.

Перед изменениями в проекте нужно читать `README.MD`, `CONTEXT.MD` и этот файл.
`README.MD` дает точку входа, `CONTEXT.MD` хранит текущие технические решения, а
`DEVELOPMENT_RULES.MD` задает постоянные правила сопровождения.

## Язык и документация

- Все новые записи в README, документации, комментариях, docstring,
  пользовательских строках и рабочих сообщениях по проекту вести на русском
  языке.
- Английские термины допустимы, если это имена команд, файлов, API, форматов,
  переменных окружения или устоявшиеся технические термины проекта.
- Для кода, связанного с release/build/deploy, SQL-миграциями, состоянием
  контуров и Windows-only pipeline, обязательны русскоязычные module docstring и
  docstring у функций с нетривиальным контрактом.
- Модульная docstring объясняет роль файла в общем release/deploy flow.
- Docstring функции описывает контракт: что функция принимает, что меняет и
  какое состояние считает источником истины.
- Для функций, которые двигают состояние релизов или контуров, явно указывается,
  меняется ли baseline.
- Для offline SQL generation явно фиксируется, что источник истины - Git range и
  локальный SQLite/manifest, а не реальная БД.
- Если алгоритм best-effort, ограничение описывается прямо в docstring.
- В задачах "только документация" или "только docstring" запрещено менять
  бизнес-логику, формат данных и поведение команд.

Эталонные файлы для стиля документации кода:

- `tools-ci/builder/scripts/additional_artifacts/create_sql_migrations.py`
- `tools-ci/builder/src/release_state.py`
- `tools-ci/simple_deploy/cli/windows_pipeline.py`
- `docs/release-sql-migrations-flow.puml`

## Правила изменения кода

- Сначала учитывать существующую архитектуру: основной поддерживаемый путь -
  Windows/Python runner в `tools-ci/`.
- Не делать широкие рефакторы, переезды файлов и изменение публичного поведения,
  если задача этого прямо не требует.
- Не смешивать разные типы изменений в одном коммите без необходимости: код,
  документация, чистка истории и операционные инструкции должны быть легко
  проверяемы отдельно.
- После изменения кода запускать релевантные тесты. Если тесты не запускались,
  прямо указать причину.
- Runtime-состояние, кэши, логи, локальные настройки и сгенерированные артефакты
  не должны попадать в Git.

## Безопасность репозитория

- Не коммитить реальные `.env`, `local.secrets.env`, vault-файлы, пароли, токены,
  приватные ключи, cookie, дампы БД и локальные state-файлы.
- Не коммитить реальные внутренние IP, логины, домены, пути локальной машины,
  названия закрытых проектов и сервисов. В примерах использовать нейтральные
  значения: `example_*`, `192.0.2.x`, `C:/example/...`, `/opt/example/...`.
- Перед публикацией изменений проверять, что в diff и истории нет чувствительных
  строк, локальных путей и проектно-специфичных идентификаторов.
- Временные директории, которые создаются в source repo во время build, должны
  удаляться после упаковки артефактов и не должны оставаться в исходном
  репозитории как мусор.

Минимальный набор проверок перед push:

```bash
git status -sb
rg -n "B[E]GIN .*PRIVATE K[E]Y|C:/w[o]rk|C:\\w[o]rk|/home/adm[i]n|10\\.1[0]\\.|10\\.9[2]\\." -S .
```

Отдельный review-проход по потенциальным секретам:

```bash
rg -n "\b(p[a]ssword|s[e]cret|t[o]ken)\b" -S .
```

Второй поиск может находить легитимные имена переменных и плейсхолдеры. Его
результат нужно просматривать вручную, а не считать автоматическим hard fail.
Список шаблонов не является исчерпывающим: если в задаче встречались конкретные
имена проектов, контуров, сервисов, логинов или путей, их нужно проверять
отдельно.

## История коммитов

- Если чувствительные или проектно-специфичные данные попали только в рабочее
  дерево, их нужно удалить обычным коммитом до публикации.
- Если такие данные уже попали в опубликованную историю, переписывать историю
  только после явного решения и с backup mirror-клоном.
- Для переписывания истории использовать отдельный mirror-клон, `git-filter-repo`
  и проверку результата по всем refs до push.
- Force-push выполнять через `--force-with-lease`, чтобы не затереть чужие
  изменения на remote.
- После переписывания истории все существующие клоны нужно синхронизировать через
  `git fetch` и `git reset --hard origin/<branch>` либо пересоздать.
- Backup mirror со старой историей считать чувствительным артефактом: хранить
  ограниченно по времени или удалять после подтверждения, что откат не нужен.

## Взаимодействие с AI-агентом

- Агент перед изменениями читает релевантные документы и код, а не строит план по
  названию задачи.
- Агент ведет рабочие сообщения по проекту на русском языке.
- Агент не меняет бизнес-логику в задачах на документацию, комментарии или
  docstring.
- Агент не удаляет данные, не переписывает историю и не делает force-push без
  явного запроса пользователя.
- Агент после изменений сообщает, какие файлы затронуты, какие проверки
  выполнены и какие риски остались.
