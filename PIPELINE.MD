# Пайплайн синхронизации, сборки и обновления локального контура

## Контекст

Проект автоматизирует односторонний перенос изменений из внешнего контура разработки
во внутренний контур и последующее обновление локального DEV-стенда.

Внешний контур - место, где работают разработчики. Внутренний контур - GitLab,
из которого код забирают безопасники и инфраструктурные процессы. Рабочая машина
имеет доступ к обоим контурам, поэтому она является точкой синхронизации, сборки
артефактов и запуска Ansible-обновления.

Текущие Python и shell-скрипты не удаляются. Они остаются сборочным этапом:
стягивают код, синхронизируют рабочие копии, собирают backend/frontend-архивы и
пушат ветки во внутренние репозитории. Новый Ansible-слой начинается после сборки:
он берет уже готовые архивы и обновляет локальный контур на VM приложения.

## Общая схема

Основная точка входа должна быть одна:

```bash
ANSIBLE_CONFIG="$PWD/ansible.cfg" .venv-ansible/bin/ansible-playbook \
  -i inventories/dev/hosts.yml playbooks/pipeline.yml
```

Этот playbook управляет всем процессом целиком. Внутри он сначала запускает
существующий `builder/create_release.py`, а затем выполняет Ansible-обновление локального
контура из созданных архивов.

Так как Ansible планируется запускать из WSL, а текущий `builder/create_release.py` использует
Windows-пути и Git Bash, сборочный шаг вызывается через переменную `build_command`.
Реальные пути внешних репозиториев, IP, порты и домены берутся не из
`group_vars/dev.yml`, а из локального `.env` в корне проекта. Корень самого
проекта и директория релизов по умолчанию вычисляются от Ansible inventory, поэтому
их не нужно указывать в обычной настройке. `group_vars/dev.yml` остается схемой
пайплайна и строит производные значения на основе `.env`.

Пайплайн разделен на четыре логических этапа:

1. Синхронизация исходников.
2. Сборка артефактов.
3. Публикация веток во внутренний GitLab.
4. Обновление локального контура через Ansible.

Такое разделение важно: сборка и раскатка имеют разные риски. Сборка работает с
репозиториями и локальными файлами, а раскатка меняет состояние VM, БД и сервисов.

## Этап 1. Синхронизация исходников

Ответственность текущих Python-скриптов.

Что происходит:

- внешние backend/frontend-репозитории переключаются на нужную ветку;
- выполняется обновление исходников;
- внутренние backend/frontend-репозитории переключаются на базовую ветку;
- создается новая синхронизационная ветка;
- содержимое внешней рабочей копии копируется во внутреннюю рабочую копию;
- служебные и тяжелые директории не переносятся: `.git`, `archives`, `build`,
  `node_modules`.

Текущая точка входа:

```bash
python builder/create_release.py
```

Роль `builder/create_release.py` сейчас - связать сборку backend и frontend одним запуском,
сгенерировать `build_version` и имя ветки. Оператору не нужно запускать его отдельно:
единый `playbooks/pipeline.yml` вызывает этот скрипт сам как внутренний сборочный шаг.

## Этап 2. Сборка артефактов

Ответственность текущих Python и shell-скриптов.

Backend:

- код переносится во внутреннюю рабочую копию;
- создается архив backend по текущей схеме `builder/scripts/archive_script_backend.sh`;
- архив попадает в директорию релиза.

Frontend:

- обновляется значение версии сборки;
- выполняется Vite-сборка;
- создаются архивы для нужных контуров через `builder/scripts/archive_script_frontend.sh`;
- для локального DEV-контура Ansible ожидает frontend-архив с `bf_dev` и
  `env_{{ frontend_server_names.dev }}` в имени.

Результат этапа:

```text
{{ release_root_wsl }}/<build_version>/
```

Внутри должны быть backend/frontend tar.gz-архивы, которые затем использует Ansible.

## Этап 3. Публикация веток во внутренний GitLab

Ответственность текущих Python-скриптов.

Что происходит:

- во внутренних backend/frontend-репозиториях создаются ветки синхронизации;
- изменения коммитятся и пушатся;
- архивы в GitLab не пушатся;
- локальный контур обновляется не из GitLab-артефактов, а из локально собранных архивов.

Такой режим оставляет GitLab источником кода и аудита изменений, но не делает его
обязательным хранилищем собранных tar.gz. В будущем можно добавить отдельный
репозиторий или хранилище артефактов, не меняя смысл Ansible-этапа.

## Этап 4. Обновление локального контура через Ansible

Ответственность Ansible.

Повторная раскатка уже собранного релиза идет через тот же единый вход, но без
повторной сборки:

```bash
ANSIBLE_CONFIG="$PWD/ansible.cfg" .venv-ansible/bin/ansible-playbook \
  -i inventories/dev/hosts.yml playbooks/pipeline.yml \
  -e run_build=false -e build_version=<build_version>
```

Отдельного пользовательского playbook для обновления локального контура больше нет.
Логика разделена на внутренние этапы `playbooks/stages/build_release.yml` и
`playbooks/stages/deploy_local_contour.yml`, которые подключает `playbooks/pipeline.yml`.

Безопасная проверка без изменений на VM:

```bash
ANSIBLE_CONFIG="$PWD/ansible.cfg" .venv-ansible/bin/ansible-playbook \
  -i inventories/dev/hosts.yml playbooks/dry_run_local_contour.yml
```

Такой dry run не требует версии билда и не проверяет конкретные архивы. Если нужно
дополнительно проверить уже собранный релиз, передайте `-e build_version=<build_version>`
или `-e use_latest_release=true`.

Ansible выполняет такие шаги:

1. Загружает конфигурацию DEV-контура из `group_vars/dev.yml`.
2. При наличии загружает секреты из `group_vars/vault.yml`.
3. Перед сборкой создает `builder/settings/*/.env` из tracked-шаблонов
   `.env.template` и подставляет домены/URL из Ansible-переменных.
4. Запускает `builder/create_release.py` с окружением `build_environment`.
5. Определяет директорию релиза по `build_version` или по новейшему релизу.
6. Находит backend/frontend-архивы по настроенным шаблонам.
7. Выполняет технические SQL-команды, если они включены для текущей фазы.
8. Выполняет сервисные команды фазы `before_unpack`, например остановку сервисов.
9. Копирует архивы на VM приложения.
10. При включенном `backup_enabled` сохраняет текущие директории деплоя.
11. Распаковывает архивы в настроенные пути backend/frontend.
12. Выполняет сервисные команды фазы `after_unpack`, если они заданы.
13. Запускает Django management-команды:
    `migrate`, затем `sync_action_role`.
14. Выполняет SQL-скрипты фазы `after_migrate`, если они заданы.
15. Выполняет сервисные команды фазы `after_migrate`, например запуск и рестарт сервисов.
16. Проверяет HTTP endpoint стенда и дополнительные healthcheck-команды.
17. Печатает итоговую сводку запуска.

## База данных

В текущей версии Ansible не дропает и не переименовывает БД.

Базовая модель:

- до обновления можно выполнить технический SQL, например `VACUUM ANALYZE`;
- в будущем можно добавить очистку логов или data-fix-скрипты;
- SQL-скрипты подключаются через `sql_scripts` и фазу выполнения;
- миграции выполняются с VM приложения через Django management-команды.

Это осознанное отличие от старой ручной инструкции с rename/drop БД. Такой сценарий
мягче для обычного обновления сервисов ППО и оставляет destructive DB-операции для
отдельного, явно управляемого процесса.

## Управление сервисами

На VM приложения много сервисов, и порядок их остановки/старта важен. Поэтому первая
версия не привязана жестко к systemd или supervisor. Вместо этого используется
упорядоченный список команд `service_steps`.

Поддерживаемые фазы:

- `before_unpack` - остановка сервисов до замены файлов;
- `after_unpack` - действия сразу после распаковки;
- `after_migrate` - запуск или рестарт после миграций.

Это временно более гибко, чем строгие Ansible-модули. Когда фактический список юнитов
и порядок стабилизируются, shell-команды можно заменить на systemd/supervisor-модули.

## Конфигурация

Основной файл настройки:

```text
.env
```

Перед реальным запуском нужно создать его из примера:

```bash
cp .env.example .env
```

И заполнить:

- пути рабочих копий backend/frontend;
- `GIT_BASH_PATH`;
- `APP_VM_HOST` и `APP_VM_USER`;
- `DB_VM_HOST`, `DB_VM_USER`, порт и имя БД;
- пути деплоя на app VM;
- `service_steps`;
- `healthcheck_commands`;
- параметры подключения к БД;
- домены dev/test/prod.

Файл `group_vars/dev.yml` не должен содержать реальные адреса конкретной машины.
Он читает `.env` и описывает, как эти значения используются в пайплайне.
`DB_VM_USER` является обязательным отдельным параметром: если пользователь DB VM
не заполнен, запуск должен падать на валидации конфигурации.

`PROJECT_ROOT_WSL`, `RELEASE_ROOT_WSL` и `RELEASE_ROOT_BASH` являются опциональными.
Их стоит задавать только если проект или директория релизов находятся не в стандартной
раскладке. `BACKEND_TARGET_REPO_PATH_BASH` нужен backend-архиватору, потому что
backend shell-скрипт работает с bash-представлением пути к репозиторию. Для frontend
отдельного `FRONTEND_TARGET_REPO_PATH_BASH` сейчас нет осознанно: frontend-архиватор
запускается из рабочей директории frontend-репозитория и использует только
`RELEASE_ROOT_BASH`.

При запуске из WSL на Windows-диске `/mnt/c` передавайте `ANSIBLE_CONFIG="$PWD/ansible.cfg"`.
Иначе Ansible может проигнорировать `ansible.cfg` из-за прав drvfs и не найти локальные роли.
SSH настроен на один парольный prompt и без повторных retries, чтобы неправильный
пароль не вводился несколько раз подряд.

Python-зависимости сборщика лежат в корневом `requirements.dev.txt`, зависимости
Ansible-слоя - в `requirements.ansible.txt`.

Для dry run на управляющей WSL-машине дополнительно нужен `netcat-openbsd`: TCP-проверки
app VM, DB VM и PostgreSQL выполняются через `nc -z -w`, чтобы недоступные адреса
становились пунктами отчета, а не подвешивали весь запуск.
Node.js/npm dry run проверяет в Windows-контексте через `cmd.exe /C`. PostgreSQL
client проверяется и используется на DB VM через SSH, поэтому управляющей WSL-машине
`psql` не нужен.

В dry run статус Ansible-задачи отделен от статуса готовности контура: `ok` означает
только успешное выполнение диагностической задачи, а результат проверки печатается
явно как `DRY-RUN PASS`, `DRY-RUN FAIL` или `DRY-RUN SKIP`.
Корневые сетевые проверки намеренно показываются как `failed ...ignoring`, если
контур недоступен: это не прерывает dry run, но не маскирует проблему под `ok`.

Секреты:

```text
group_vars/vault.yml
```

Файл `vault.yml` не хранится в git. Его нужно создать на основе
`group_vars/vault.example.yml` и зашифровать через `ansible-vault`.

## Точки расширения

Запланированные направления развития:

- параметризовать ветки внешних и внутренних репозиториев;
- заменить hardcoded пути в Python-сборке на конфигурацию;
- добавить отдельное хранилище артефактов;
- добавить откат через release-директории и symlink `current`;
- формализовать список сервисов и перейти от shell-команд к Ansible-модулям;
- добавить отдельный playbook для destructive DB-операций, если они снова понадобятся;
- добавить отчет о commit SHA backend/frontend, из которых собран релиз.

## Граница ответственности

`playbooks/pipeline.yml`:

- основная единая точка входа;
- запускается вручную или по расписанию;
- подключает внутренний этап подготовки релиза;
- подключает внутренний этап обновления локального контура;
- скрывает от оператора техническое разделение процесса на этапы.

`builder/create_release.py`:

- остается внутренней точкой сборочного этапа;
- генерирует версию и ветку;
- запускает backend/frontend-сборку;
- готовит локальные архивы;
- пушит код во внутренние репозитории.

Ansible:

- в едином playbook управляет всем процессом;
- в dry run сначала проверяет локальные Git-репозитории, наличие `origin` URL и
  сетевую доступность полной ссылки origin через `curl --head --location`;
- `git ls-remote origin` в dry run не используется, потому что HTTPS-origin может
  требовать интерактивную авторизацию;
- ограничивает системные, Git, TCP и PostgreSQL-проверки dry run таймаутом
  `dry_run_command_timeout_seconds`;
- сам код собирает через существующий `builder/create_release.py`;
- не пушит архивы;
- не заменяет текущие сборочные скрипты;
- обновляет локальный контур из уже собранного релиза;
- выполняет технические DB-команды, миграции, рестарт сервисов и healthcheck.
