# Builder

Builder собирает переносимый пакет релиза для конкретной версии. Его задача -
подготовить директорию релиза с продуктовыми архивами, SQL-артефактами и
`release_manifest.json`, которые затем использует Windows runner или ручной
процесс продвижения на контуры.

Builder не является самостоятельным runner-ом деплоя и не заменяет локальное
состояние simple-deploy. Он готовит содержимое релиза, но не применяет его на
VM и не двигает baseline контуров.

## Что входит в пакет релиза

В директории релиза builder формирует:

- runtime-архив backend;
- архивы frontend, которые собираются для поддерживаемых контуров;
- schema SQL-архивы для `dev`, `test`, `prod`;
- `release_manifest.json` с версией релиза, commit SHA исходных репозиториев и
  описанием артефактов.

Data SQL из docs не собираются. В manifest сохраняется
`artifacts.backend_db.db_data_sql_enabled=false`, а ключи data SQL-архивов
отсутствуют. Старые флаги и `SIMPLE_DEPLOY_INCLUDE_DATA_SQL=1` их не включают.
Во временный `build_scripts` копируется только `create_sql_migrations.py`.
Отдельный источник и разовый процесс data SQL отложены в
[backlog](../../PRODUCT_BACKLOG.MD).

До сборки проверяются обе пары source/target: одинаковый каталог, в том числе
через junction/symlink, запрещён. Проверка повторяется в компонентных builder-ах
и функциях синхронизации до операций с файлами.

Такой пакет переносим как набор файлов релиза: его можно передать в runner,
использовать для ручного SQL-продвижения TEST/PROD или хранить как описание
конкретной сборки.

## Что не входит в пакет релиза

В пакет релиза намеренно не входят:

- секреты, SSH-доступы и локальные `tools-ci/.env`/`tools-ci/local.secrets.env`;
- `tools-ci/windows_pipeline.local.json` и операторские runtime-настройки;
- локальная SQLite-база `local_state/simple_deploy.sqlite3`;
- состояние baseline контуров;
- сам runner деплоя и его окружение выполнения;
- VM/DB окружение;
- default maintenance stub из `tools-ci/maintenance_stub/maintenance_stub.tar.gz`.

Эти данные остаются локальным состоянием рабочей машины или инфраструктуры. При
деплое runner берет пакет релиза как вход, а правила применения, доступы,
baseline и фиксацию результата читает из runtime-конфигурации и
SQLite-состояния.

## Источник истины

Для содержимого конкретного релиза источником истины является
`release_manifest.json` и файлы в директории релиза. Для операционного состояния
контуров источником истины остается SQLite-состояние simple-deploy.

Успешная сборка релиза добавляет запись о релизе и попытке сборки в SQLite, но не
означает успешное применение на `dev`, `test` или `prod`. Baseline двигается
только после успешного деплоя или явной ручной фиксации результата.
