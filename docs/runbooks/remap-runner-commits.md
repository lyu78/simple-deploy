# Перенос baseline после переписывания Git history

Команда `python -m simple_deploy.cli.remap_commits` переводит текущие backend
source commits контуров по карте `git-filter-repo`. Её можно подготовить на
одной машине, а запустить позже на рабочем runner. Рабочая база нужна только
при запуске. Требуются Python 3.10+, установленный пакет `simple-deploy` и Git;
дополнительные зависимости для маппера не нужны.

## Что переносится

Меняются только `contour_state.last_success_backend_commit` и `updated_at`
для существующих записей DEV/TEST/PROD. Номер последнего успешного релиза
сохраняется. История `releases`, build/deploy attempts, frontend commits,
файлы manifest и SQL-архивы сохраняют прежние значения.

Это замена идентификатора того же состояния после переписывания истории,
а не применение нового релиза. Команда не выполняет SQL приложения, не
подключается к PostgreSQL и не делает Git fetch/pull/checkout.

## Что перенести на рабочую машину

1. Обновлённый `simple-deploy` с этой maintenance-командой.
2. Файл `commit-map` именно того переписывания, которое затронуло source.
   Обычно он находится в `.git/filter-repo/commit-map`, а у bare-репозитория —
   в `filter-repo/commit-map`. `ref-map` для этой операции не подходит.
3. Рабочую копию backend source с новой историей и веткой сборки `dev`.

Карту и резервные копии храните вне Git, например в игнорируемом
`local_state/commit-remap/`. Реальные SHA и локальные пути не добавляйте
в tracked-документацию. Маппер не использует `.env` и не выбирает базу сам:
`--db`, `--commit-map` и `--source-repo` обязательны. Если runner использует
`SIMPLE_DEPLOY_STATE_DB`, передайте в `--db` именно этот путь.

## Предварительный просмотр

Из корня `simple-deploy` в PowerShell задайте свои пути:

```powershell
$remapArgs = @(
    '--db', 'C:/example/simple-deploy/local_state/simple_deploy.sqlite3',
    '--commit-map', 'C:/example/simple-deploy/local_state/commit-remap/commit-map',
    '--source-repo', 'C:/example/repos/backend-source'
)
.venv/Scripts/python.exe -Xutf8 -m simple_deploy.cli.remap_commits @remapArgs
```

Без `--apply` выполняется только чтение. Явный `--dry-run` эквивалентен
режиму по умолчанию. Вывод содержит путь к базе, SHA-256 карты, source ref,
старый/новый SHA каждого контура и блокирующие ошибки. Код возврата `0`
означает готовый план или отсутствие необходимых изменений; `1` — ошибку.

Проверки:

- формат карты и уникальность старых SHA;
- полные SHA или однозначные сокращения длиной не менее семи символов;
- отсутствие удалённых SHA (`new` из нулей) и неизвестных соответствий;
- наличие новых commit-объектов в указанном backend source;
- принадлежность новых commit-ов истории `dev`;
- отсутствие `running` jobs и `started` build/deploy attempts.

При необходимости `--source-ref` задаёт другую ветку проверки; это не меняет
ветку, которую использует обычный builder. По умолчанию проверяется `dev`,
а не текущая checkout-ветка. Не проверяйте SHA по target-репозиторию.

Карта считается доверенным результатом переписывания. Проверка существования
и ancestry нового SHA не доказывает неизменность содержимого Django-миграций
или соответствие реальной БД. Если при переписывании менялись сами миграции,
сначала сверяйте их с ранее применённым состоянием отдельно.

## Применение

Остановите worker и web/API, завершите CLI build/deploy и внешние операции
с этой базой. Не запускайте их до окончания переноса. Оставшиеся после сбоя
`running`/`started` записи требуют отдельного разбора; маппер их не исправляет.

После просмотра плана выполните с теми же аргументами:

```powershell
.venv/Scripts/python.exe -Xutf8 -m simple_deploy.cli.remap_commits @remapArgs --apply
```

Команда повторно проверяет план под блокировкой записи SQLite, создаёт рядом
с исходной базой согласованную копию
`<имя базы>.before-commit-remap-<timestamp>-<id>.sqlite3`, проверяет её и только
после этого обновляет baseline. Backup включает committed данные WAL.
Все контуры изменяются одной транзакцией: ошибка любого контура отменяет
весь перенос. При ошибке записи уже созданная копия остаётся рядом с базой.

Повторный запуск той же карты распознаёт уже переведённые SHA и не меняет
базу повторно. В этом случае дополнительный backup не создаётся. Пустая
или отсутствующая база считается ошибкой; новые baseline не инициализируются.

Если SHA удалён, отсутствует в карте/source или неоднозначен, команда
останавливается. Подбирать вместо него `HEAD` автоматически нельзя.

После переноса повторите предварительный просмотр и обычный `dry-run` на
рабочем runner, затем собирайте новый релиз из новой истории. Перенос SHA
сам по себе не адаптирует источник SQL из `docs` и не решает другие вопросы
совместимости структуры репозиториев.

Старые manifest сохраняют старые SHA. Команды `mark-applied` и `set-baseline
--build-version` для старого релиза могут вернуть старый SHA в contour state.
Не используйте их для восстановления перенесённого baseline без отдельного
разбора; новые релизы будут содержать SHA новой истории.

## Восстановление

Backup содержит всю базу до переноса. Если требуется откат до последующих
build/deploy, остановите все процессы runner-а и восстанавливайте SQLite
из этой копии. Учитывайте WAL: не заменяйте только основной файл работающей
базы, оставляя её старые `-wal`/`-shm`. Восстановление полной базы также
откатывает историю операций, записанных после backup.
