# Перенос baseline после переписывания Git history

Команда `python -m simple_deploy.cli.remap_commits` переводит текущие backend
source commits контуров по карте `git-filter-repo`. Карта текущего переноса
включена в пакет и приезжает с обновлением simple-deploy: отдельно копировать
`commit-map` на рабочую машину не требуется. Рабочая база нужна только при
запуске. Требуются Python 3.10+, установленный пакет `simple-deploy` и Git;
дополнительные зависимости сверх настроенного runner-а не нужны.

## Короткий запуск из Git Bash

1. Дождитесь завершения build/deploy и остановите web/API и worker.
2. Обновите simple-deploy. Backend source должен уже содержать новую историю
   и локальную ветку `dev`.
3. Из корня simple-deploy посмотрите соответствия SHA:

   ```bash
   ./remap-commits.sh
   ```

4. Если просмотр завершился без ошибок и показывает нужные базу/source,
   примените перенос:

   ```bash
   ./remap-commits.sh --apply
   ```

5. Повторите `./remap-commits.sh`: изменений больше не должно требоваться.
   После этого можно запускать web/API и worker.

Launcher использует `.venv/Scripts/python.exe` из этого checkout и переходит
в корень simple-deploy. Source читается из `BACKEND_SOURCE_REPO_PATH` в
`tools-ci/.env`. SQLite выбирается той же функцией registry, что у web/worker:
`SIMPLE_DEPLOY_STATE_DB` из окружения процесса либо
`local_state/simple_deploy.sqlite3`. Если отдельное значение этой переменной
в `.env` указывает на другую базу, маппер остановится и попросит явный `--db`.
Маппер не читает файл секретов и не создаёт отсутствующую SQLite.

Без `--apply` выполняется только чтение. Launcher сам не запускает build,
deploy, обычный `dry-run`, web или worker.

## Что переносится

В обычном режиме меняются только `contour_state.last_success_backend_commit` и `updated_at`
для существующих записей DEV/TEST/PROD. Номер последнего успешного релиза
сохраняется. История `releases`, build/deploy attempts, frontend commits,
файлы manifest и SQL-архивы сохраняют прежние значения.

Это замена идентификатора того же состояния после переписывания истории,
а не применение нового релиза. Команда не выполняет SQL приложения, не
подключается к PostgreSQL и не делает Git fetch/pull/checkout.

## Встроенная карта и явные пути

По умолчанию используется ресурс пакета
`simple_deploy/registry/commit_maps/backend-history-v1.map`. Это полная карта
подготовленного переноса: только пары SHA, включая отметки об удалённых
коммитах, без путей, содержимого исходников и учётных данных. Она включается
и в Git checkout, и в устанавливаемый Python-пакет.

Для другого переписывания можно передать `--commit-map /path/to/commit-map`.
Такой файл должен относиться именно к нужной смене истории; `ref-map` не
подходит. Внешние карты и резервные копии храните вне Git, например в
игнорируемом `local_state/commit-remap/`. Реальные SHA и локальные пути не
добавляйте в tracked-документацию.

Параметры `--db`, `--source-repo`, `--env-file` и `--commit-map` необязательны:
они переопределяют автоматический выбор. Если одновременно заданы `--db` и
`--source-repo`, `.env` не читается и зависимости настроенного runner-а для
разрешения путей не нужны. База для записи всегда выводится в плане.

## Предварительный просмотр

При необходимости явных путей из корня `simple-deploy` в PowerShell:

```powershell
$remapArgs = @(
    '--db', 'C:/example/simple-deploy/local_state/simple_deploy.sqlite3',
    '--source-repo', 'C:/example/repos/backend-source'
)
.venv/Scripts/python.exe -Xutf8 -m simple_deploy.cli.remap_commits @remapArgs
```

Без `--apply` выполняется только чтение. Явный `--dry-run` эквивалентен
режиму по умолчанию. Вывод содержит путь к базе, SHA-256 карты, source ref,
старый/новый SHA каждого контура и блокирующие ошибки. Код возврата `0`
означает готовый план или отсутствие необходимых изменений; `1` — ошибку.

Проверки:

- формат карты и уникальность старых SHA;
- полные SHA или однозначные сокращения длиной не менее семи символов;
- отсутствие удалённых SHA (`new` из нулей) и неизвестных соответствий;
- наличие новых commit-объектов в указанном backend source;
- принадлежность новых commit-ов истории `dev`;
- отсутствие `running` jobs и `started` build/deploy attempts; явный режим
  `--close-interrupted` включает их завершение в план вместо этой блокировки.

При необходимости `--source-ref` задаёт другую ветку проверки; это не меняет
ветку, которую использует обычный builder. По умолчанию проверяется `dev`,
а не текущая checkout-ветка. Не проверяйте SHA по target-репозиторию.

Карта считается доверенным результатом переписывания. Проверка существования
и ancestry нового SHA не доказывает неизменность содержимого Django-миграций
или соответствие реальной БД. Если при переписывании менялись сами миграции,
сначала сверяйте их с ранее применённым состоянием отдельно.

## Прерванные операции после остановки процессов

Сообщение о незавершённых операциях означает наличие статусов `running` в
`local_jobs` или `started` в `build_attempts`/`deployment_attempts`. Это проверка
записей SQLite, а не фактической работы процессов. После аварийного завершения
такие записи могут остаться. Маппер выводит таблицу, ID и время начала каждой.

Если web, worker, CLI build/deploy и их дочерние процессы действительно
остановлены, посмотрите план закрытия этих записей вместе с переносом SHA:

```bash
./remap-commits.sh --close-interrupted
```

Проверьте перечисленные записи. Для применения:

```bash
./remap-commits.sh --close-interrupted --apply
```

Флаг означает явное подтверждение оператора, что процессы остановлены.
Маппер не определяет это по возрасту записи и не останавливает процессы сам.
Без `--apply` статусы и baseline остаются прежними.

После backup перечисленные записи получают `failed`, время завершения и
пояснение о ручном закрытии как прерванных. Предыдущая ошибка сохраняется.
ID, исходные SHA попыток, payload, пути к логам и остальные поля сохраняются;
задания `queued` и уже завершённые операции не меняются. Этот режим не
фиксирует успешное применение релиза и не запускает SQL приложения.

Перед записью под блокировкой SQLite повторно сверяется полный снимок записей,
а не только их количество. Закрытие операций и перенос SHA выполняются одной
транзакцией: при ошибке откатываются оба изменения. Ошибки карты и проверки
новых SHA остаются блокирующими. Если SHA уже перенесены, можно закрыть только
прерванные операции; повторный запуск без изменений не создаёт новый backup.

## Применение

Остановите worker и web/API, завершите CLI build/deploy и внешние операции
с этой базой. Не запускайте их до окончания переноса. Для подтверждённых
оператором прерванных `running`/`started` записей используйте описанный выше
режим `--close-interrupted`; обычный запуск продолжает их блокировать.

После просмотра плана выполните с теми же аргументами:

```powershell
.venv/Scripts/python.exe -Xutf8 -m simple_deploy.cli.remap_commits @remapArgs --apply
```

Команда повторно проверяет план под блокировкой записи SQLite, создаёт рядом
с исходной базой согласованную копию
`<имя базы>.before-commit-remap-<timestamp>-<id>.sqlite3`, проверяет её и только
после этого обновляет baseline. Backup включает committed данные WAL.
Все контуры изменяются одной транзакцией: ошибка любого контура отменяет
весь перенос. При ошибке записи уже созданная копия остаётся рядом с базой.

Повторный запуск той же карты распознаёт уже переведённые SHA и не меняет
базу повторно. В этом случае дополнительный backup не создаётся. Пустая
или отсутствующая база считается ошибкой; новые baseline не инициализируются.

Если SHA удалён, отсутствует в карте/source или неоднозначен, команда
останавливается. Подбирать вместо него `HEAD` автоматически нельзя.

После переноса повторите предварительный просмотр и обычный `dry-run` на
рабочем runner, затем собирайте новый релиз из новой истории. Перенос SHA
сам по себе не адаптирует источник SQL из `docs` и не решает другие вопросы
совместимости структуры репозиториев.

Старые manifest сохраняют старые SHA. Команды `mark-applied` и `set-baseline
--build-version` для старого релиза могут вернуть старый SHA в contour state.
Не используйте их для восстановления перенесённого baseline без отдельного
разбора; новые релизы будут содержать SHA новой истории.

## Восстановление

Backup содержит всю базу до переноса. Если требуется откат до последующих
build/deploy, остановите все процессы runner-а и восстанавливайте SQLite
из этой копии. Учитывайте WAL: не заменяйте только основной файл работающей
базы, оставляя её старые `-wal`/`-shm`. Восстановление полной базы также
откатывает историю операций, записанных после backup.
